# 与主控聊天 vs 与员工聊天 — 区别说明

本文档基于 `panel-web/server.js` 与前端逻辑整理，说明两种对话在技术实现与使用场景上的差异。

---

## 一、概览对比

| 维度 | **与主控聊天** | **与员工聊天** |
|------|----------------|----------------|
| 前端入口 | 项目页「与主控对话」面板 | 项目页「与员工协作」面板 |
| 后端接口 | `POST /api/yin/chat` | `POST /api/agent/chat` |
| 轮询结果 | `GET /api/yin/task/:taskId` | `GET /api/agent/task/:taskId` |
| 调用对象 | **单个**主控网关（阴） | **多个**员工网关（员工） |
| 网关端口 | 固定 `18789`（主控） | 各员工独立端口（如 18791、18801…） |
| 对话角色 | 用户 ↔ 主控（1 对 1） | 用户 ↔ 多名员工（1 对多，群聊式） |
| 是否多轮讨论 | 否，单轮请求-回复 | 是，支持 1～5 轮群讨论（员工之间可见彼此回复） |
| 是否使用工具 | 否，仅文本对话 | 否（此处仅 chat）；工具执行走 `agent-task` |
| 历史存储 | `chat_yin_{projectId}.json` | `chat_discuss_*` / `chat_single_*`（按模式） |

---

## 二、与主控聊天（阴 / Yin）

### 作用

- 用户与**主控（Command Core）**对话，主控作为「指挥中枢」：
  - 知晓当前项目、已选员工、项目记忆；
  - 可看到**员工群讨论**的最近内容（只读摘要），用于回答「群里在聊什么」「讨论进展如何」并给出决策建议；
  - 可被用户要求在本项目中选员工、启动员工等（主控侧可调接口/逻辑配合）。
- 适合：**定策略、要决策、查进展、派活**，而不是直接和某个员工你一句我一句。

### 技术要点

- **请求**：`POST /api/yin/chat`，body 含 `message`、`projectId`、`history`。
- **下游**：请求**主控网关** `http://127.0.0.1:18789/v1/chat/completions`（与终端主控 TUI 同一进程）。
- **上下文注入**（在 `buildYinMessages` 中）：
  - 项目 ID、名称、已选员工列表；
  - 项目记忆（最近若干条）；
  - **员工群讨论摘要**：`readHexDiscussForYin(projectId)` 从 `chat_discuss_{projectId}.json` 取最近若干条，压缩后以 system 形式注入，主控据此「监控」群聊并回答用户。
- **历史**：主控对话历史压入 `chat_yin_{projectId}.json`，与员工聊天历史分离。
- **鉴权**：主控网关 Token 来自 `OPENSWARM_GATEWAY_TOKEN` 或 `yin/moltbot.json` 等。

### 特点小结

- 单点（主控）、单轮请求-回复。
- 主控「能看到」员工群讨论摘要，但不直接代替员工发言。
- 适合：问主控要结论、要排期、要谁来做，而不是和多个员工一起多轮讨论。

## 三、与员工聊天（员工 / Hex / 员工协作）

### 作用

- 用户在本项目中与**多个数字员工**一起对话：
  - **群发单聊**：同一句话发给多个员工，各员工独立回复，彼此看不到对方回复；
  - **群讨论**：多轮（1～5 轮），每轮员工可看到其他员工的回复，形成真实「群聊」；
  - **执行任务**：通过「派发任务」走 `agent-task`，员工可执行工具（写文件、执行命令等），此处 chat 只做文字对话。
- 适合：**头脑风暴、分工讨论、方案碰撞**，或对多员工同时发指令。

### 技术要点

- **请求**：`POST /api/agent/chat`，body 含 `message`、`hexIds`（可选，不传则用项目全部员工）、`history`、`enableBroadcast`、`maxRounds`、`projectId`。
- **下游**：对**每个**目标员工请求其网关 `http://127.0.0.1:{port}/v1/chat/completions`，端口在 `workers.conf` 等配置中按员工分配。
- **模式**：
  - **单聊（broadcast=false）**：只把用户消息 + 用户历史发给每个员工，员工之间不共享彼此回复。
  - **群讨论（broadcast=true）**：
    - 第 1 轮：用户消息发给所有员工，并行请求，收集每人回复；
    - 第 2 轮：把「用户消息 + 所有员工第 1 轮回复」再发给每个员工，每人基于「群聊上下文」再回一条；
    - 第 3～5 轮：继续把当前讨论全文给有回复的员工，做收口或深度讨论。
- **@ 提及**：消息里可 `@员工名`，接口通过 `parseMentionedHexIds` 解析，只给被 @ 且在项目中的员工发请求。
- **上下文注入**：每个员工收到项目名称、项目 ID、参与员工列表、项目记忆、产出路径规则（`workspace/output/{projectId}/`）等，通过 system 消息注入。
- **历史**：按模式写入 `chat_discuss_*` 或 `chat_single_*`，与主控的 `chat_yin_*` 分开。

### 特点小结

- 多点（多员工）、可多轮、可群讨论。
- 员工之间可看到彼此回复（在群讨论模式下），适合协作讨论。
- 仅文字对话，不执行工具；工具执行走 `/api/agent/agent-task`（WebSocket + agent 命令）。

## 四、群讨论里员工之间如何协调与执行任务

群讨论（`enableBroadcast: true`）下，员工之间的「协调」完全通过**共享上下文 + 多轮文本回复**完成，没有员工主动调用另一名员工或自动派发子任务的机制；真正的「执行」由用户在讨论后通过「派发任务」显式触发。

### 4.1 多轮讨论中的信息共享（协调方式）

- **共享上下文**  
  每个员工在每一轮收到的 system 里都包含：
  - 当前项目名称、项目 ID、参与员工列表；
  - 项目记忆（最近若干条）；
  - 产出路径规则：`workspace/output/{projectId}/`。

- **第 1 轮**  
  - 用户一条消息 + 历史（群讨论模式下含既往群聊）发给**所有**目标员工，并行请求。
  - 各员工只看到「用户 + 历史」，看不到本轮其他员工的回复；各自独立生成第一条回复。
  - 服务端收集所有回复到 `hexReplies`，用于第二轮。

- **第 2 轮**  
  - 构建「群聊全文」：用户消息 + 所有员工第 1 轮回复（带员工名）。
  - 对**除自己外**的每个员工，用同一份全文再发一条 user 消息，例如：「以上是群聊中的对话。A 说："…"。你可以基于这些对话继续讨论。」
  - 即：每个员工都会看到「所有人第 1 轮的发言」，并基于此生成「看到其他员工回复后」的补充；服务端把同一员工的多条补充拼成一条（如追加 `[看到其他员工的回复后] ...`）。
  - 因此，第 2 轮起员工之间是通过**看到同一份讨论全文**来「对齐信息」的，没有点对点调用。

- **第 3～5 轮**  
  - 继续把**当前讨论全文**（用户 + 所有轮次已产生的员工回复）发给本轮仍参与的员工。
  - 每轮追加一条 user 提示，例如：「以上是当前讨论（第 N 轮）。请基于上面所有观点，补充你的新看法或进一步论证（如无新观点可说「无」）。」
  - 最后一轮会提示「请再简短补充一句收口（可选，无则说「无」）」。
  - 协调方式仍然是：**同一份全文 + 自然语言提示**，没有结构化分工或自动委派。

小结：员工之间的「协调」= **共享同一份讨论上下文**（项目信息 + 历史 + 每轮所有人回复），通过多轮 prompt 让每人基于「别人说了什么」再补充，纯文本、无 API 互相调用。

### 4.2 从讨论到执行：谁在派活

- **群讨论本身不执行任务**  
  - `/api/agent/chat` 只调各员工网关的 `POST /v1/chat/completions`，只做对话；员工在讨论中**不能**调用工具、不能写文件、不能执行命令。
  - 因此，讨论阶段没有任何「员工 A 给员工 B 派活」或「员工自动执行某步骤」的机制。

- **执行任务由用户显式派发**  
  - 用户点击「⚡ 派发任务」后，前端用 `buildDiscussContext()` 从当前群讨论缓存（`_hexChatCache['discuss']`）中取出最近若干条（用户、员工、讨论摘要、主控决策等），拼成「讨论背景」。
  - 用户填写「执行指令」并勾选要执行的员工（可多选）。
  - 前端对**每个**被选中的员工各发一次 `POST /api/agent/agent-task`，body 里：
    - `hexId`：该员工 ID；
    - `message`：`【背景讨论记录】\n{讨论背景}\n\n【你的执行任务】\n{用户输入的指令}`（若有讨论背景），或仅用户指令；
    - `projectId`、`sessionKey` 等。
  - 服务端对每个请求走 WebSocket 调用该员工的 agent，员工在**自己的**上下文中执行（可跑工具、写文件等）。多名员工收到的是**同一份**背景 + 同一份任务描述，但**各执行各的**，没有服务端层面的「A 派给 B」逻辑。

- **讨论摘要与主控决策**  
  - 群讨论结束后，前端可让某一员工生成「讨论摘要」；用户可再点「@主控 请求决策」，把摘要发给主控，主控返回「决策 / 理由 / 行动项」等。
  - 这些摘要和决策会进入 `buildDiscussContext()` 的上下文（类型 `summary` / `decision`），在用户点击「派发任务」时一并作为「背景讨论记录」传给被选中的员工，从而把「讨论结论 / 主控决策」和「执行指令」一起交给执行者。

### 4.3 总结

| 环节           | 协调/执行方式 |
|----------------|----------------|
| 讨论中信息对齐 | 服务端把「用户 + 所有人已发内容」作为共享上下文，每轮发给各员工；员工只通过文本回复「看到别人说了什么」并补充，无互相调用。 |
| 讨论中执行任务 | 无；群讨论仅对话，不跑工具、不派子任务。 |
| 讨论后执行任务 | 用户点击「派发任务」，选员工、写指令；讨论背景（含摘要/主控决策）自动带入，每个被选员工独立收到一条 agent-task，各自执行。 |
| 多员工同一任务 | 用户可多选员工；每人收到同一份「背景 + 指令」，并行执行，互不委派。 |

因此：**群讨论里的「协调」是「共享上下文 + 多轮文本」；「执行」是用户主导的「派发任务」+ 单员工 agent-task，没有员工之间的自动委派或任务链。**

## 五、与 agent-task（执行任务）的对比（接口维度）

| 能力 | 与主控聊天 | 与员工聊天 | agent-task（派发任务） |
|------|------------|------------|------------------------|
| 对象 | 主控 | 多员工 | 单员工 |
| 协议 | HTTP chat completions | HTTP chat completions | WebSocket agent |
| 输出 | 主控一段回复 | 每员工一段/多段回复 | 执行结果 + chat.history 最新 assistant |
| 工具/执行 | 无 | 无 | 有（exec、fs_write 等） |
| 多轮 | 无（每次单轮） | 有（1～5 轮群讨论） | 由 agent 内部多步 |

---

## 六、总结一句话

- **与主控聊天**：和「指挥中心」对话，看项目与群聊摘要、要决策和安排；单点、单轮。
- **与员工聊天**：和「多个员工」一起聊，可多轮群讨论、可 @ 指定人；多点、可多轮，仅文字，不跑工具。
- **派发任务（agent-task）**：让**单个员工**真正执行任务（写文件、跑命令等），走 WebSocket + 工具。
